## Solution

A .NET 10 solution: a pure conversion class library with no I/O, an EF Core class library, and an ASP.NET Core Web API host that also serves a React + TypeScript + Vite single-page application from the same origin. In development the host starts Vite and forwards to it, so the browser only ever talks to `https://localhost:7162`; in production it serves the built files with an `index.html` fallback, and unknown `/api` paths answer 404 JSON. EF Core runs on SQLite locally (created with `EnsureCreated`, recreated when the model changes) and on MySQL when hosted (Microting provider), with migrations generated for MySQL only, never run at startup, and applied by me as an idempotent script. Add an exact `/health` endpoint, anonymous, GET and HEAD only, first in the pipeline, reporting status, version, commit and time without touching the database or any external service; a `versions.json` at the repository root; a Dockerfile on port 8080; security headers and a content security policy; rate limits per client; OpenAPI; an `AGENTS.md`; and GitHub Actions for CI only (build, tests, lint, dictionary check, Docker build, no cloud credentials).

Tests in xUnit: golden tables for the converter, and API tests through the real pipeline on temporary SQLite files, with fakes for every external service (identity provider, email, WhatsApp, DeepL, Bedrock, AWS). No test ever touches a real service.

Four skills in `.claude/skills`: linked notes (every C# file explains its decisions in a sibling `.notes.md` nested under it in the project, no explanatory comments in code), task closure (build and test without hitting real services, update notes and docs, append the prompt history, check privacy, and report honestly whether a change is prepared, committed or published), React patterns (folders `app/ components/ pages/ services/ types/ routes/ config/ hooks/ i18n/ utils/`, one HTTP client, no `any`, no `console.log`, every visible text through `t("English sentence")`, design-system components) and styles without modules (global BEM kebab-case CSS, no `.module.css`, no `!important`, colours and sizes only through semantic `:root` tokens).

## The converter

Conversion happens on the server. The input is the task's format: up to 999 999 999 dollars and 99 cents, digits grouped in blocks of three by spaces, a comma before one or two cent digits, so `25,1` is ten cents. Refuse anything else with a precise code the interface translates (a point as decimal separator gets a hint to use a comma). The six examples of the task are golden tests in every language.

Write one speller class per language that owns the whole sentence, because the grammar where the number meets the currency differs in each language. Languages: English (US, the default), Brazilian Portuguese, German, French, Italian, Spanish, Polish, and the Asian languages of kla.com's own language menu: Simplified Chinese, Traditional Chinese, Japanese and Korean, counting in myriads. French comes in four variants, which is especially interesting: France and Canada say "quatre-vingt-dix", Belgium "nonante", and Switzerland "nonante" and "huitante"; keep a section on the page that shows those variants. The output language follows the interface language and can be changed independently, and a comparison shows the same amount in every language. Any count shown on the page (output languages, variants of French) is computed, never hardcoded.

We will implement two kinds of conversion: deterministic, the reference, and AI-based, on Amazon Bedrock with Claude: the Converse API, a configurable application inference profile, prompt caching, strict JSON output, few-shot examples generated by the rules engine, and only the validated amount reaches the model. Show the AI answer next to the rules engine's with an "agrees / differs" badge. Log every call with tokens, cost and latency, and guard it with a kill switch, a monthly USD ceiling, a daily cap, a per-client cap and a concurrency gate.

## Translations

Translation is the proof of concept of a system I designed to make a multi-language app easy to extend: put a value in an enum, and the app is translated into the language of that value. It covers the JavaScript/TypeScript interface and the backend messages (emails and API error messages) alike. If you have suggestions of improvements that don't change the idea, they are welcome.

- An `InterfaceLanguage` enum on the server is the only list of languages: code, native name, the DeepL target only when a rule cannot derive it, and the parent of a regional variant. The web client builds its language menu from the server and keeps a copy only as a fallback.
- The English source text is the key. Terms and translations live in database tables (`Terms` and `Translations`, with the source of each translation and a `Reviewed` flag).
- The dictionaries for every language also ship with the app, complete and checked in CI, so a clone is fully translated offline; on start they are imported as reviewed translations.
- Texts no dictionary knows are registered by the interface and by the server, and a background batch translates every missing one through DeepL: up to 50 texts per request, exponential backoff that honours `Retry-After`, a clean stop when the quota is used up, `{{placeholders}}` protected with `tag_handling=xml` and `ignore_tags`, English declared as the source. The public registration endpoint is capped (text size, per client per day, per day, rate limit, antiforgery), and so are the DeepL characters per day.
- A dictionary endpoint per language, versioned by a hash of its content and served with an ETag. The language comes from `?lang=`, then a cookie, then `Accept-Language`. Regional variants inherit from their parent and store only what differs; they are never machine-translated.
- An admin screen, only for configured administrator addresses: edit and review translations (hand edits are never overwritten by the machine or by the bundled import), translate now, and export a language in the bundled dictionaries' format so reviewed texts can be committed.

## Accounts and sign-in

Access to the platform is public. Signing in is only needed to send a result to yourself and to keep your last conversions, and the only way in is OpenID Connect with fmID, my own identity provider at mourafelipe.com; this application stores no passwords. fmID is built in my personal website's codebase (a private repository, used only by me) by another Claude Code session; coordinate the contract with it directly, and if something would be better implemented there instead of here, tell me. The provider is OpenIddict: authorization code with PKCE (S256 only), query response mode, confidential clients registered through a command-line command (one production client and one `-dev` client with a localhost callback per consumer), scopes `openid profile email phone`, claims `sub`, `name`, `email`, `email_verified`, `phone_number` and `phone_number_verified`, no roles in tokens, short-lived codes and tokens, no refresh tokens, signing and encryption certificates stored as SecureString parameters in AWS Systems Manager and read at startup, and RP-initiated logout. Registration, email confirmation, password reset and the WhatsApp number (confirmed with a code) happen on the provider's pages.

In this application, implement the consumer side: register the `OpenIdConnect` scheme with `SignInScheme = External`, never store tokens, challenge and sign out only through POST with antiforgery, send the interface language as `ui_locales`, map refusals to error codes in the query string, link the provider's subject to a local account only through a verified address, and issue the application's own cookie through `SignInManager.SignInAsync(user)`. The client secret comes from a secret store through an environment variable.

Email goes through Amazon SES v2 from kla@mourafelipe.com, with a configuration set, an HTML part and a plain-text part, no dollar amount in the subject, and a bounce subdomain of mine as custom MAIL FROM so SPF aligns with my domain. WhatsApp goes through the Meta Cloud API from the business number I already own, with a pre-approved utility template in every language Meta accepts and English as the fallback, to the number verified on fmID; if that number was checked more than ten minutes ago, refresh it with a silent sign-in before sending. Log every send with a masked destination.

Signed in, the converter also lists the visitor's last conversions (ten per account, at most 90 days old) on any device; choosing one converts it again, and the list can be cleared.

## Guardrails

We need a mechanism that caps the number of WhatsApp messages, emails and AI calls and does not depend on the code, since the code will be public. The person who holds the code must not have control over the infrastructure: no growing the database, no sending millions of WhatsApp messages or billions of emails. Keep the caps in AWS Systems Manager Parameter Store, read-only for the application, failing closed (a missing cap is zero), and count usage atomically in the database. We have a budget of 15 dollars a month for the pay-per-use services (AI, WhatsApp, email, and DeepL on its Free plan); size the caps to it, with a monthly cap for WhatsApp, since Meta may bill the result template at the marketing rate. Give the application a least-privilege task role (SES only from that address and configuration set, Bedrock only on its inference profile, read-only parameters under its own path), a MySQL runtime user without DDL rights and with hourly limits, alarms that notify me, a kill switch, and a 90-day retention for personal data.
